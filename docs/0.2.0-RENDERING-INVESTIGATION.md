# VOID FPS 0.2.0 development — rendering investigation

## Verified source state
- The client entrypoint currently registers only `BenchmarkRecorder`.
- No mixin configuration or rendering mixins are present in the inspected source paths.
- The benchmark recorder is opt-in through `-Dvoidfps.benchmark=true`; it logs once-per-second FPS, heap use and process CPU. It does not optimize rendering.
- The development branch uses Minecraft 26.3, Fabric Loader 0.19.5, Fabric API 0.164.0+26.3 and Java 25.

## Minecraft 26.3 bytecode facts in the repository
The checked bytecode for `SectionCompiler.compile(SectionPos, RenderSectionRegion, VertexSorting, SectionBufferBuilderPack)` shows:
1. A `SectionCompiler$Results`, `VisGraph`, `ModelBlockRenderer`, `FluidRenderer` and per-layer builder map are created for a section compile.
2. The method iterates the 16×16×16 block positions in the section.
3. Air states are skipped.
4. Opaque states are recorded in `VisGraph`.
5. Block entities are collected.
6. Non-empty fluid states are tessellated.
7. Model blocks are passed to `ModelBlockRenderer.tesselateBlock(...)`.
8. Completed meshes are built; translucent mesh quads are sorted; the block-model lighter cache is cleared and the visibility set is resolved.

The inspected `ModelBlockRenderer` bytecode also shows reusable per-instance state such as a mutable scratch position, quad instance, random source, part list and tint caches. This is a warning against adding duplicate caches or allocating replacements in the hot path.

## Profiling evidence available in the conversation
Previously pasted JFR execution samples included worker-thread stacks through Indigo block-model emission, `SectionCompiler.compile`, fluid tessellation, ambient occlusion and chunk-generation scheduling. Main-thread samples included entity ticking and `LevelRenderer` render preparation.

These are sampled stacks, not method-duration measurements. The recording included early world-entry activity, so they do not prove which method dominates steady-state gameplay. The large `gameplay-final.txt` upload was confirmed present in the repository, but its contents were not successfully retrieved for analysis. No claim is made that it was fully analyzed.

## What is deliberately NOT implemented yet
No rendering mixin is enabled in this development snapshot. The current bytecode alone does not identify a semantics-preserving shortcut inside the 4096-position scan, and changing that scan risks omitting block entities, fluids, visibility data, or model output. Vanilla already performs face culling in the block-model pipeline; reimplementing it would be redundant.

## Next engineering gate
Before adding a runtime optimization:
- inspect the exact target method and all relevant call sites from the 26.3 jar;
- identify a redundant operation that can be removed without changing output;
- add a narrow mixin with a verified descriptor and a safe fallback;
- compile against the exact local dependency set;
- launch the client and check blocks, lighting, AO, tint, fluids, transparency and block entities;
- compare repeatable vanilla/modded frame-time measurements at the same camera position and scene.

Only measured improvements should remain enabled. No FPS gain is claimed by this document.
